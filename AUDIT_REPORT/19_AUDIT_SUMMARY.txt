EXECUTIVE SUMMARY
================================================================================
Audit of backend file operations revealed GOOD overall security architecture
but 2 VULNERABILITIES requiring fixes:

1. SYMLINK TRAVERSAL (Medium Severity)
   - Location: backend/src/lib/upload.ts:44-45 (removeUploadedFile function)
   - Risk: Admin can delete files outside /uploads via symlinks if created
   - Exploit: ln -s /etc backend/uploads/offers/pw; then API call deletes /etc/passwd
   - Requirement: Server-side write access (already compromised if possible)
   - Fix: Add fs.lstat() check to detect symlinks before deletion

2. DOUBLE URL ENCODING (Low Severity)
   - Location: backend/src/lib/upload.ts:43 (removeUploadedFile function)
   - Risk: Encoded paths (..%2f..%2f) bypass traversal check
   - Impact: Minimal because filenames from multer (UUID) never contain /, %
   - Requirement: Relies on DB containing malicious imageUrl (doesn't happen)
   - Fix: Add decodeURIComponent() to normalize encoded paths

3. PERMISSION MISCONFIGURATION (Low Severity)
   - Location: backend/uploads/ directory (755 permissions)
   - Risk: OS users can read/execute uploaded files
   - Impact: Low in containerized environments, OK if process isolation is strong
   - Fix: chmod 750 (or restrict in Dockerfile)

================================================================================
FINDINGS BY SEVERITY
================================================================================

CRITICAL: None
-----------
No critical vulnerabilities found. No remote path traversal possible via web API.

MEDIUM: Symlink Traversal
-----------
File:   backend/src/lib/upload.ts, lines 42-47
Code:   removeUploadedFile(imageUrl)
Issue:  fs.stat() follows symlinks; attackers with OS access can create
        symlink in uploads/ pointing to /etc, then trigger deletion
Proof:  Testing shows: /uploads/offers/symlink-to-etc/passwd
        → /home/mateo/prim-o/backend/uploads/offers/symlink-to-etc/passwd
        → Passes startsWith() check (VULNERABLE)
Fix:    Use fs.lstat() instead of stat() and check isSymbolicLink()

MEDIUM: Double URL Encoding
-----------
File:   backend/src/lib/upload.ts, line 43
Code:   removeUploadedFile(imageUrl)
Issue:  decodeURIComponent() not called; double-encoded paths bypass check
Example: /uploads/offers/..%252f..%252fetc → not decoded by removeUploadedFile
Impact: Low - imageUrl always from DB (server-generated UUID)
Fix:    Wrap imageUrl.replace() with decodeURIComponent()

LOW: Restrictive Permissions
-----------
File:   backend/uploads/
Perms:  755 (rwxr-xr-x)
Issue:  All OS users can read + list uploaded files
Fix:    chmod 750 in Dockerfile or startup script

================================================================================
VULNERABILITY SCENARIOS
================================================================================

Scenario 1: Direct Path Traversal (BLOCKED ✓)
─────────────────────────────────────────────
Attack: POST /api/admin/offers/{id}/image with filename "../../etc/passwd"
Result: multer generates UUID instead (BLOCKED)

Attack: DELETE /api/admin/offers/{id}/image with malicious imageUrl
Result: imageUrl from DB, set by server (no injection possible)

Scenario 2: URL Traversal (BLOCKED ✓)
──────────────────────────────────────
Attack: GET /api/uploads/../../etc/passwd
Result: express.static() blocks .. sequences (BLOCKED)

Scenario 3: Symlink Traversal (VULNERABLE ⚠)
──────────────────────────────────────────────
Attack: Create symlink in uploads/offers via compromised OS access
        ln -s /etc uploads/offers/pw
        Then trigger deletion via admin API
Result: File matches startsWith check → DELETES /etc/passwd (VULNERABLE)
Fix:    Add fs.lstat() check (see recommendations)

Scenario 4: Double Encoding (LOW RISK ⚠)
───────────────────────────────────────────
Attack: Database contains imageUrl: /uploads/offers/..%252f..%252fetc
        (double-encoded)
Result: decodeURIComponent() not called → Tries to delete literal filename
        "..%252f..%252fetc" (which never exists)
Fix:    Add decodeURIComponent() (see recommendations)

Scenario 5: Symlink + Double Encoding (VERY LOW RISK)
──────────────────────────────────────────────────────
Attack: Symlink in DB URL: /uploads/offers/link%252fpasswd
        (escaped and pointing to symlink to /etc)
Result: File with name containing literal %252f doesn't exist → fails
Impact: VERY LOW because (a) needs DB compromise, (b) filename unlikely
