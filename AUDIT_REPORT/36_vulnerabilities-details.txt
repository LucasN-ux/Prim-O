DETAILED VULNERABILITY ANALYSIS
================================

VULNERABILITY #1: MISSING MAGIC BYTE VALIDATION (CWE-434)
=========================================================

Severity: MEDIUM (HIGH impact, but mitigated by static serving)
CVSS v3.1 Score: 5.3 (Medium)
CWE: CWE-434 (Unrestricted Upload), CWE-434 (Improper Restriction of Rendered UI)

Location:
  File: backend/src/lib/upload.ts
  Lines: 31-37 (fileFilter only checks mimetype, not file content)

Description:
The upload handler validates only the multipart Content-Type header (file.mimetype),
which is CLIENT-CONTROLLED and can be spoofed. Actual file binary signatures are never
checked.

Attack Scenario:
1. Attacker creates malicious file: shell.php (contains: <?php system($_GET['cmd']); ?>)
2. Attacker uploads with Content-Type: image/jpeg in multipart headers
3. Server accepts (mimetype='image/jpeg' passes fileFilter)
4. File stored as: backend/uploads/offers/[uuid].jpg
5. Browser requests /api/uploads/offers/[uuid].jpg
6. Static server serves with Content-Type: image/jpeg (correct)
7. Browser receives as image, tries to render, fails silently
8. NO EXECUTION because:
   - Node.js express.static is NOT a CGI handler
   - PHP files are NOT executed server-side
   - Content-Type is image/jpeg, browser cannot execute

Current Mitigation:
- Static file serving (Node.js, not Apache/IIS with PHP)
- JPG/PNG/WebP served as images (browser cannot execute binary)
- No PHP CGI handler configured

Risk Assessment:
- If backend is later deployed to Apache/IIS with PHP: CRITICAL
- Current Node.js setup: LOW RISK (mitigated by static serving)
- If .jpg files later interpreted as PHP: CRITICAL

Proof of Concept (demonstrates vulnerability, but doesn't exploit):
```bash
# Create PHP file
echo '<?php phpinfo(); ?>' > /tmp/shell.php

# Upload with spoofed MIME type
curl -X PATCH http://localhost:4000/api/admin/offers/123e4567-e89b-12d3-a456-426614174000/image \
  -H "Authorization: Bearer [ADMIN_TOKEN]" \
  -F "image=@/tmp/shell.php;type=image/jpeg"

# Server accepts because:
# - fileFilter checks file.mimetype = 'image/jpeg' ✓
# - No magic byte check (vulnerability!)

# Verify file was stored
ls /home/mateo/prim-o/backend/uploads/offers/
# Output: [uuid].jpg (PHP code inside, but safe due to static serving)
```

Recommended Fix:
```typescript
import { fileTypeFromBuffer } from 'file-type';

// Map allowed MIME types to magic bytes
const ALLOWED_SIGNATURES = {
  'image/jpeg': [0xFF, 0xD8, 0xFF],
  'image/png': [0x89, 0x50, 0x4E, 0x47],
  'image/webp': [0x52, 0x49, 0x46, 0x46], // RIFF header
};

fileFilter: async (_req, file, cb) => {
  // First check: MIME type header
  if (!ALLOWED.has(file.mimetype)) {
    return cb(new Error('INVALID_IMAGE_TYPE'));
  }
  
  // Second check: magic bytes (requires buffer access in multer)
  // Note: multer's fileFilter doesn't have easy buffer access
  // Alternative: validate in destination callback after stream
  cb(null, true);
}
```

Better approach: Use middleware to check magic bytes:
```typescript
import { fileTypeFromBuffer } from 'file-type';

const validateMagicBytes = async (_req, _file, cb) => {
  // Read file buffer from disk after multer writes
  // Validate magic bytes match MIME type
};
```

VULNERABILITY #2: IMPLICIT EXPRESS.JSON LIMIT (CWE-400)
=======================================================

Severity: LOW
CVSS v3.1 Score: 3.7 (Low)
CWE: CWE-400 (Uncontrolled Resource Consumption)

Location:
  File: backend/src/app.ts
  Line: 68

Description:
express.json() is called without explicit limit parameter. While Express 5.x defaults
to 100kb (safe), this is implicit and not enforced by documentation.

Current State:
```javascript
app.use(express.json());
// Defaults to 100kb in Express 5.x
```

Risk:
- Image upload uses multipart (not JSON), so no impact here
- JSON payload endpoints could theoretically accept larger payloads
- Express default (100kb) is safe, but not explicit
- Future dev might assume no limit and build large JSON APIs

Impact:
- Minimal on this project (image upload is multipart)
- Improves code clarity and prevents future regressions

Recommended Fix:
```javascript
app.use(express.json({ limit: '1mb' }));
```

VULNERABILITY #3: NO EXPLICIT MULTIPART LIMIT (CWE-400)
========================================================

Severity: LOW
CVSS v3.1 Score: 3.7 (Low)
CWE: CWE-400 (Uncontrolled Resource Consumption)

Location:
  File: backend/src/lib/upload.ts
  Line: 31-37

Description:
multer is configured with fileSize limit (2MB), but NOT with field limits or overall
multipart limits.

Current Configuration:
```javascript
export const offerImageUpload = multer({
  storage,
  limits: { fileSize: 2 * 1024 * 1024 }, // ✓ file size limited
  fileFilter: (_req, file, cb) => {
    // no fieldSize or partSize limit
  },
}).single('image');
```

Potential Attack:
```bash
# Attacker sends multipart with many fields (but single file within limit)
# Each field has overhead; accumulative memory pressure
# Example: 100 fields × 1MB overhead = 100MB memory

curl -X PATCH http://localhost:4000/api/admin/offers/123/image \
  -H "Authorization: Bearer [TOKEN]" \
  -F "image=@file.jpg" \
  -F "field1=data" \
  -F "field2=data" \
  ... (1000 times)
```

Risk: LOW
- .single('image') rejects all but one field
- Multer refuses extra fields by default
- fileSize limit (2MB) prevents large payload

Current Mitigation:
- .single('image') only accepts ONE file field
- Other fields are parsed but ignored (no memory bomb)

Recommendation (Defense-in-Depth):
```javascript
export const offerImageUpload = multer({
  storage,
  limits: {
    fileSize: 2 * 1024 * 1024, // 2 MB per file
    files: 1,                   // max 1 file
    fields: 1,                  // max 1 field
    fieldSize: 1 * 1024,        // max 1 KB per field
  },
  fileFilter: (_req, file, cb) => {
    if (ALLOWED.has(file.mimetype)) cb(null, true);
    else cb(new Error('INVALID_IMAGE_TYPE'));
  },
}).single('image');
```
